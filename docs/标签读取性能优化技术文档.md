# 标签读取性能优化技术文档

> 适用版本：MusicTagRecover（WPF / .NET 10 / x64）
> 优化范围：目录批量扫描的标签读取链路、内存管理、输出裁剪
> 测试样本：`F:\新建文件夹`（1363 个 FLAC / 74.7 GB）

---

## 1. 优化目标与达成指标

| 指标 | 优化前（TagLibSharp2） | 优化后（MediaInfo） | 变化 |
|---|---|---|---|
| 扫描完成时间 | 35.2 s | 5.4 s | 6.5× 提速 |
| 文件读取速度 | 38.7 文件/秒 | 243~254 文件/秒 | 6.3× |
| 工作集峰值增量 | +8,146 MB | +133 MB | ↓ 98.4% |
| 工作集均值增量 | +4,840 MB | +67 MB | ↓ 98.6% |
| 托管堆峰值增量 | +5,891 MB | +5 MB | ↓ 99.9% |
| Gen2 GC 次数 | 94 | 4 | GC 风暴消除 |
| 输出目录体积 | 760 MB | 205 MB | ↓ 555 MB |

## 2. 根本原因分析

### 2.1 内存暴涨根因

TagLibSharp2（T2）解析音频文件时，会把内嵌封面**整张读入托管内存**——`T2.IPicture.PictureData` 类型为 `Memory<byte>`，即解析期字节就已分配完毕。轻量扫描虽然只消费 `PictureData.Length`，但分配无法避免：

```
每个 FLAC 封面 ≈ 数百 KB ~ 数 MB
1363 个文件 × 8 路并行 → LOH（大对象堆）高速分配/回收
→ Gen2 GC 风暴（94 次）→ 工作集峰值 +8.1 GB
```

### 2.2 速度瓶颈根因

T2 为解析封面需把封面字节从磁盘读入，单文件 IO 量 = 标签头 + 全部封面数据（数 MB）；
MediaInfo 只读媒体头与标签文本字段（数 KB），从不导出封面字节（实测 `CoverInfo.Data` 为空数组）。
IO 量差三个数量级，是 5~6 倍速度差的来源。

### 2.3 次要因素

- 旧加载路径一次性物化全部文件的 `Task` 对象（`files.Select(async ...)` + `Task.WhenAll`），千级任务/闭包造成额外堆分配。
- TagLib 回退路径先调用全量映射（复制整张封面字节/歌词正文）再丢弃，属纯浪费。
- `MediaInfo.Core.Native` NuGet 包附带约 40 个 Linux/macOS 运行时变体（libmediainfo.so/dylib，合计约 540MB），本应用 `PlatformTarget=x64` 永不加载。

## 3. 架构设计

### 3.1 读取链路分层

```
┌─────────────────────────────────────────────────────────────┐
│ UI 层：MainViewModel.LoadStateAsync（有界并行调度）            │
├─────────────────────────────────────────────────────────────┤
│ 服务层：FileScannerService.ScanDirectoryAsync（并行工作池）    │
├─────────────────────────────────────────────────────────────┤
│ 引擎层：TagService.ReadTagsSummaryAsync / ReadTagsAsync        │
│   ┌──────────────┬────────────────────────────────────────┐ │
│   │ 轻量摘要读取   │ 全量读取（选中单文件）                    │ │
│   │ summaryOnly  │ summaryOnly = false                    │ │
│   ├──────────────┼────────────────────────────────────────┤ │
│   │ ① MediaInfo  │ ① TagLibSharp2（标签+封面+歌词全量）     │ │
│   │ ② TagLib     │ ② TagLib 补充（作词者/FLAC 封面/码率）   │ │
│   │   PictureLazy│ ③ TagLib 全量回退                       │ │
│   │ ③ T2 轻量    │                                        │ │
│   └──────────────┴────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────────┘
```

### 3.2 三级回退链（轻量扫描）

```
ReadAudio(filePath, summaryOnly: true)
  │
  ├─ ① TryReadSummaryViaMediaInfo     ← 主路径：速度/内存最优
  │     成功 → 返回
  │     失败（Success=false / 异常）↓
  ├─ ② TryReadSummaryViaTagLibLazy    ← 兜底：封面字节磁盘惰性
  │     成功 → 返回
  │     失败（TagLib 不支持该格式）↓
  └─ ③ TagLibSharp2 轻量路径           ← 罕见格式（DSF/DFF/MPC 等）
```

设计原则：**任何单引擎解析失败都不影响数据产出**，格式覆盖范围不小于优化前。

### 3.3 为什么轻量路径不全量使用 TagLib PictureLazy

PictureLazy 方案（封面字节惰性化）实测同样可达亚秒级（0.86s 热缓存），但：
- MediaInfo 在原生层完成解析，托管堆增量（+5MB）低于 TagLib 惰性方案（+194MB）；
- 封面计数、歌词存在性等元数据 MediaInfo 直接以字段返回，无需进入托管对象图；
- 低层绑定可按字段精确查询约 20 项，免去 TagLib 完整标签对象图的构建。

## 4. 核心算法与实现

### 4.1 MediaInfoScanReader —— 低层绑定读取器

位置：`Services/TagService.cs`（`MediaInfoScanReader`，私有嵌套类）

**为何绕过 MediaInfoWrapper**：wrapper 每次构造会构建视频流/音频流/字幕/章节等全部对象并查询数百个字段，单文件开销大；且未实现 `IDisposable`，原生句柄依赖终结器回收——批量扫描时原生内存滞留，进程退出时偶发原生崩溃。

**核心机制**：

```csharp
private sealed class MediaInfoScanReader : IDisposable
{
    private readonly MediaInfo.MediaInfo _mi = new();

    // 原生 Open 返回空指针即解析失败（触发回退链）
    public bool Open(string filePath) => _mi.Open(filePath) != IntPtr.Zero;

    // 按字段名精确查询：General 流（标签/时长/封面标志）与 Audio 流（码率/采样率）
    public string General(string name) => _mi.Get(StreamKind.General, 0, name);
    public string Audio(string name)   => _mi.Get(StreamKind.Audio, 0, name);

    public void Close() => _mi.Close();
    public void Dispose() => _mi.Dispose();   // 确定性释放原生句柄
}
```

**使用模式**（`TryReadSummaryViaMediaInfo`）：

```csharp
using var reader = new MediaInfoScanReader();
if (!reader.Open(filePath)) return null;   // → 回退 TagLib PictureLazy
// …逐字段映射…
reader.Close();
return data;
```

### 4.2 字段映射算法

| TagData 字段 | MediaInfo 参数 | 说明 |
|---|---|---|
| Title / Artist / Album | `Title` / `Performer` / `Album` | General 流 |
| AlbumArtist | `Album/Performer` | 专辑艺术家 |
| Composer / Lyricist / Genre / Comment | 同名参数 | |
| Year | `Released_Date` → `Recorded_Date` | `ParseYear4`：扫描首个连续 4 位数字（兼容 `"2013"`/`"2013-05-01"`/`"UTC 2013-…"`），合法域 1600–2100 |
| Track / TrackCount | `Track/Position`（+`_Total`） | `SplitPosition`：兼容 `"3"` 与 `"3/12"` 两种写法 |
| Disc / DiscCount | `Part/Position`（+`_Total`） | 同上 |
| DurationMs | `Duration` | 毫秒，直接 long 解析 |
| BitRate | `BitRate`（Audio 流）→ `OverallBitRate` | **单位换算 bps→kbps**（`Math.Round(rate/1000)`） |
| SampleRate / Channels | `SamplingRate` / `Channels` | |
| BitsPerSample | `BitDepth` | |
| TagFormat | `Format` | 如 `FLAC`、`MPEG Audio` |
| PictureCount | `Cover == "Yes"` → 1 | MediaInfo 只报有无，不报张数（0/1 语义） |
| CoverArtMimeType / Type | `Cover_Mime` / `Cover_Type` | |
| LyricsPresent | `Lyrics` 非空 | 只判断存在性，不持有正文 |

**单位陷阱**：`MediaInfo.MediaInfo` 的 `BitRate` 返回 **bps**（实测 FLAC 返回 1757310），而 `TagData.BitRate` 全应用统一为 **kbps**（TagLib 约定）。优化前视频路径存在 bps 当 kbps 的既有缺陷，本次在 `MapMediaInfoToTagData` 中一并修正。

### 4.3 封面与歌词的"零内存"策略

- **封面**：MediaInfo 仅返回 `Cover/Cover_Mime/Cover_Type` 元数据，不导出图片字节——这是峰值内存下降两个数量级的根本原因。代价是计数只有 0/1，扫描列表场景可接受；选中文件后全量路径仍返回真实张数与字节。
- **歌词**：仅通过 `General("Lyrics")` 判非空，`TagData.Lyrics` 保持 null，列表行只记录 `HasLyrics` 布尔。
- **兜底路径同等约束**：`TryReadSummaryViaTagLibLazy` 以 `ReadStyle.Average | PictureLazy` 打开，封面帧只读头部；`MapToSummaryData` 精简映射跳过作词者、不复制任何字节。

### 4.4 并行调度与内存控制

**FileScannerService**：

```csharp
// 并行度按 CPU 核数 4~8 自适应：T2 各格式读取相互独立（无共享句柄），
// 上限防止机械盘高队列深度抖动
public static int ScanParallelism { get; } =
    Math.Clamp(Environment.ProcessorCount, 4, 8);
```

**MainViewModel.LoadStateAsync**：`Parallel.ForEachAsync` 有界拉取替代 `files.Select(async …)` 全量物化——工作项按需进入线程池，避免上千个 Task/闭包的一次性分配。

**扫描后回收**（既有机制保留）：逐行 `ReleaseDetails()` 释放旧目录封面/歌词引用 → `GC.Collect(2, Forced, true, true)` 压缩式回收 → `TrimWorkingSet` 裁剪工作集，保证切换到小文件夹后内存快速回落。

### 4.5 全量读取路径的 T2 缺陷修正

优化过程中暴露并修复了 TagLibSharp2 0.6.0 的两个既有缺陷（第三方权威解析验证）：

1. **FLAC 封面不暴露**：T2 已解析 PICTURE 块字节但未映射到 `Tag.Pictures`（`Pictures=0`，而 TagLib 权威解析为 1 张 image/jpeg 34KB）。
   → `MergeLegacyPictures`：全量读取零封面时用 TagLib 补全 `AllPictures/CoverArtData/PictureCount`。
2. **FLAC 码率恒为 2304**：TagLib 与 MediaInfo 独立计算均为 ~1757kbps。
   → `OverrideLegacyBitRate`：FLAC 全量读取用 TagLib 计算值覆盖。

### 5.2 TagData（数据契约，关键字段）

```csharp
public class TagData
{
    // 文本标签
    string? Title / Artist / Album / AlbumArtist / Composer / Lyricist / Genre / Comment;
    uint? Year / Track / TrackCount / Disc / DiscCount;

    // 音频属性（BitRate 统一 kbps）
    long? DurationMs;  int? BitRate / SampleRate / Channels / BitsPerSample;

    // 封面：轻量模式只有 PictureCount/MimeType/Type；全量模式另有字节
    int PictureCount;  string? CoverArtMimeType / CoverArtType;
    byte[]? CoverArtData;  List<CoverArt>? AllPictures;

    // 歌词：轻量模式只有 LyricsPresent；全量模式另有 Lyrics 正文
    bool LyricsPresent;  string? Lyrics;

    bool IsSummary;      // 标记轻量读取结果
    string? TagFormat;   // 格式描述
}
```

## 6. 输出裁剪（构建目标）

`MusicTagRecover.csproj` 新增构建后目标：

```xml
<Target Name="TrimRedundantNativeRuntimes" AfterTargets="Build"
        Condition="Exists('$(OutDir)runtimes')">
  <!-- 仅保留 runtimes\win-x64；删除其余 ~40 个 Linux/macOS RID 目录与根目录 x86\ -->
</Target>
```

效果：输出目录 760MB → 205MB。保留项：`x64\MediaInfo.dll`（wrapper 显式加载路径）、`runtimes\win-x64`、ffmpeg（功能依赖）、`mac\MACDll64.dll`（Monkey's Audio Windows 编解码库，勿按目录名误解）。

注意：MSBuild 通配符 `runtimes\*` 无法可靠匹配目录，实现使用
`$([System.IO.Directory]::GetDirectories(...))` 内建函数精确列举后再排除 `win-x64`。

## 8. 已知取舍与后续建议

| 事项 | 说明 |
|---|---|
| 封面计数 0/1 | MediaInfo 不报告张数；全量路径（TagLib）仍返回真实张数 |
| Duration ±1~2ms | MediaInfo 与 TagLib 舍入差异，显示无感 |
| BitRate ±1kbps | MediaInfo 四舍五入 vs TagLib 截断 |
| TagFormat 语义变化 | 由标签容器（如 `FLAC · Vorbis Comment`）变为容器格式（`FLAC`） |
| MediaInfo 失败回退 | DSF/DFF/MPC 等自动落到 TagLib/T2，功能不缩水 |
